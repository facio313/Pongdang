기존 Pongdang 프론트엔드의 디자인과 사용자 흐름을 보존하면서, 아래 A1~A8 전체와 B의 AI 선행 기반에 필요한 독립 백엔드를 구현·통합·검증하고, 현재 화면에 연결할 수 있는 기능은 최소한의 데이터 연결 수정으로 연동하라. 프론트가 없는 기능도 백엔드 구현을 완료하고 API와 인계 문서를 제공하라.

나는 경수이며 Pongdang의 백엔드 담당자다.
이 요청은 계획서 작성이나 코드 검토만을 요청하는 것이 아니라 실제 구현 요청이다.
분석 후 구현, 테스트, 수정, 연결, 인계까지 계속 진행하라.

현재 요청이 구현 범위를 정하며, 실제 구현은 Pongdang의 독립성·데이터 진실성·검증 계약을 유지해야 한다.
레거시의 예시 점수, 임계값, 진행률, 완료 표시를 검증된 사실로 간주하지 말라.
필요한 외부 API의 현재 명세와 제공 조건은 최신 공식 문서로 확인하라.


2. 내 역할과 이번 작업의 범위

나는 백엔드 담당자이므로 아래 기능에 필요한 서버 측 작업을 빠짐없이 구현해야 한다.

각 기능에 필요한 다음 요소를 실제 사용 가능한 수준으로 연결하라.
- 데이터 모델과 명시적 DB migration
- 데이터 수집·정규화·저장 및 필요한 입력 경로
- 도메인 로직과 계산·판정·비교 로직
- 필요한 worker/job과 주기 실행
- 조회 API 및 기능에 필요한 인증된 변경 API
- 오류·결측·만료·외부 서비스 실패 처리
- 자동 테스트와 통합 검증
- OpenAPI 및 프론트엔드 인계 문서

프론트엔드가 아직 없거나 다른 담당자의 작업으로 표시되어 있다는 이유로 백엔드를 생략하지 말라.
이미지의 80%, 20%, 60%, 0%는 참고용 메모다.
실제 코드와 실행 근거를 확인하여 구현 상태를 판단하라.

기존에 정상 구현된 기능은 보존하고 부족한 부분만 보완하라.
특히 기존 Water Index의 판정기, 불변 근거 저장, assessments/support/coverage API를 확인하여 중복 구현을 피하라.


3. 프론트엔드 보존과 연결 범위

작업 시작 시 현재 Git 상태와 기존 변경사항을 기록하라.
커밋되지 않은 수정과 추가 파일도 보존해야 할 현재 작업 결과다.
다른 작업자의 변경을 되돌리거나 덮어쓰지 말라.

기존 프론트엔드의 다음 요소를 유지하라.
- 디자인, CSS, 레이아웃, 컴포넌트 구조
- 메뉴, 라우팅, 페이지 구성
- 사용자 흐름과 기존 기능
- 현재 연결된 실제 데이터 표

백엔드 연동에 필요한 다음 최소 수정은 허용한다.
- API client
- 전용 DTO 타입과 런타임 응답 검증
- 데이터 조회 hook
- 기존 결과 영역의 데이터 바인딩
- 실제 API 상태를 정확히 반영하기 위한 로딩·오류·빈 값 처리

연결을 이유로 화면을 새로 디자인하거나 페이지 전체를 재작성하지 말라.
새 지도·차트·알림 설정 화면 등 새로운 UI가 필요한 기능은 백엔드와 계약을 먼저 완성하고, 프론트 담당자가 연결할 수 있도록 인계하라.
기존 화면에 표시할 자리가 없는 결과를 억지로 새 UI로 추가하지 말라.

프론트 수정이 발생하면 파일별로 “어떤 API를 연결하기 위해 무엇을 바꿨는지”를 설명하고,
화면 구조와 디자인을 보존했는지 확인하라.

현재 /pongdang/ 배포 경로와 Vite BASE_URL, FastAPI root_path를 유지하라.
api.ts의 기존 경로 구성과 useResource.ts의 요청 취소·조건 변경 처리를 확인하여 경로 중복이나 오래된 응답 노출을 막아라.
새 평가 응답을 기존 일반 자료표 타입으로 강제 단언하지 말라.


4. 기능별 필수 구현

A1. Water Index — 물 여행 적합도 지수

장소·활동·대상 시각 또는 기간을 기준으로 환경과 활동 조건을 평가하는 백엔드를 완성하라.

- 기존 water_index 엔진·계약·저장 구조를 먼저 확인하여 확장한다.
- 실제 Pongdang 수집자료를 평가 입력과 조회 가능한 결과로 연결하는 producer 및 필요한 job을 구현한다.
- 장소와 관측소, 활동 지원, 공식 주의·제한 정보의 연결 근거와 적용 범위를 보존한다.
- 활동 지원, 안전·제한, 환경 적합도, 선호, 입력 품질을 서로 구분한다.
- 계산에 사용한 입력, 원자료 revision, 계산식·모델·파라미터 버전, 평가 시각과 근거를 재현할 수 있게 한다.
- 수치 모델이 필요하면 기존 연구·설계를 바탕으로 구현하고, 미확정 파라미터와 검증 과제를 명시적으로 관리한다.
- 소프트웨어 테스트 통과를 과학적 검증 완료로 바꾸지 않는다.
- 검증되지 않은 점수나 추천 순위를 공개하기 위해 임의 가중치·기본값을 넣지 않는다.
- 필요한 근거나 검증이 부족한 결과는 null/unknown과 구체적인 사유를 반환한다.

“점수가 아직 검증되지 않았다”는 이유로 입력 연결, 평가 실행, 저장, 조회, 상태 설명, 테스트까지 미루지 말라.


A2. Water Forecast — 미래 물 예보

장소·활동·기간별로 실제 공식 예보를 소비하고 결과를 제공하는 백엔드를 구현하라.

- 기상·해양·조석 등 기존 예보 수집 경로와 A1 계약을 재사용한다.
- 예보 발표 시각, 대상 시각·기간, 수집 시각, 제공기관과 수정 이력을 보존한다.
- 관측값, 공식 예보, 별도 추정값을 구분한다.
- 제공기관이 실제 제공한 시간 해상도와 예보 범위를 유지한다.
- 7일 화면을 채우기 위해 없는 미래 값을 만들거나 현재 관측값을 복제하지 않는다.
- 자료 범위 안의 결측과 예보 범위 밖 요청을 구분한다.
- 예보 상태와 평가 결과를 저장·조회하고, 이후 그래프나 달력에 연결할 수 있는 계약을 제공한다.
- 방문 시점 추천은 해당 추천 규칙과 검증 조건이 충족되는 범위에서만 제공한다.


A3. Water Twin — 실시간 디지털 트윈 지도

지도 UI와 독립적으로 사용할 수 있는 장소별 상태·레이어 조회 백엔드를 구현하라.

- 장소 좌표, 장소 유형, 관측소 연결, 레이어별 상태와 출처를 제공한다.
- 지도 범위, 장소, 활동, 시각 등 필요한 조회 조건을 지원한다.
- 지리 범위와 결과 수를 제한하고 기존 최대 100행 페이지 원칙을 유지한다.
- 바다·계곡·온천·갯벌 등에 필요한 정보를 실제 확보된 자료 범위에서 반환한다.
- 최신 관측과 과거 관측, 예보, 결측, 만료를 구분한다.
- A1·A2·A4 결과를 일관된 장소·시간 기준으로 소비할 수 있게 한다.
- 조회 한 번에 장소별 외부 API를 반복 호출하는 구조를 만들지 않는다.

새 지도 UI 구현을 백엔드 완료의 선행조건으로 두지 말라.


A4. 실시간 수온 지도

Water Twin에서 재사용할 수 있는 수온 전용 조회 기능을 구현하라.

- 실제 수온, 단위, 관측소, 좌표, 측정·수집·만료 시각을 제공한다.
- 관측소 값이 대표하는 공간과 연결된 여행 장소의 관계를 명시한다.
- 가까운 관측소의 수온을 해당 해변에서 직접 측정한 값처럼 표시하지 않는다.
- 관측과 예측·추정을 구분한다.
- 지도 범위·시각·장소 조건과 제한된 페이지 조회를 지원한다.
- 보간을 추가한다면 별도로 검증된 방법·적용 범위·불확실성을 갖추고 estimated로 구분한다.
- 수온 수집 성공만으로 입수 가능이나 안전을 판정하지 않는다.


A5. 라이브캠 물멍 허브

실제 공개 라이브캠을 장소와 연결하여 제공하는 백엔드를 구현하라.

- 제공기관, 공개 제공 페이지, 장소 연결, 재생 방식, 임베드 가능 여부와 사용 조건을 관리한다.
- 확인된 공식 공개 자료를 대상으로 재생·연결 상태와 최근 확인 시각을 관리한다.
- 라이브 영상, 녹화 영상, 정지 이미지, 오프라인, 확인 불가를 구분한다.
- 조회·필터·상태 확인과 필요한 주기 점검을 구현한다.
- 실제 검증된 영상이 없으면 자료 없음으로 반환한다.
- 인증정보가 포함된 upstream URL을 노출하거나 임의 URL을 프록시하는 기능을 만들지 않는다.
- 더미 영상이나 무관한 영상을 실제 현장 라이브처럼 제공하지 않는다.


A6. 물때 액티비티 타이머

조석 자료를 기반으로 다음 물때와 활동 관련 시간 정보를 제공하는 백엔드를 구현하라.

- 실제 조석 예측과 고저조 시각을 사용한다.
- 장소·관측소 매핑, 지역 날짜와 시간대, 다음 간조·만조를 처리한다.
- 프론트가 countdown을 표시할 수 있도록 기준 시각과 이벤트 시각을 제공한다.
- 자정을 넘는 시간창, 자료 만료, 예측 정정, 이벤트가 없는 경우를 처리한다.
- 활동 시간창의 근거와 규칙 버전을 보존한다.
- 간조 전후 일정 시간을 임의로 정하여 안전한 갯벌 체험 시간이라고 선언하지 않는다.
- 공식·현장 운영 시간과 통제 조건이 확인되는 범위에서만 활동 가능 시간으로 제공한다.
- 필요한 알림 이벤트는 A7과 공유할 수 있는 기반으로 구현한다.


A7. “올해 첫 입수 가능” 알림

찜하거나 구독한 장소의 조건 변화를 감지하는 백엔드를 구현하라.

- 장소·사용자 설정·연도에 따른 구독, 조건 평가, 이벤트 생성과 이력을 구현한다.
- 기존 SSO와 권한 구조를 활용하고 새 계정 체계를 만들지 않는다.
- 필요한 구독 변경·해지·조회 API와 접근 권한 검증을 구현한다.
- 중복 이벤트 방지, 재시도, 발송 상태, 실패, 취소 및 조건 변경을 처리한다.
- 프로세스 재시작 후에도 상태를 유지한다.
- 연중 관측 이력이 부족하면 “올해 최초”라고 확정하지 않는다.
- 기획서의 22~23℃를 검증된 안전 기준으로 하드코딩하지 않는다.
- 수온 조건 충족 이벤트와 실제 입수 안전 판정을 분리한다.
- 발송 provider와 필요한 실제 adapter를 구현하고 설정·오류 처리까지 검증한다.
- 자격증명이나 발송 채널이 없는 경우 테스트 대역으로 경로를 검증하고 미설정 상태를 명확히 반환한다.

개발 중 실제 사용자에게 알림을 보내지 말라.
실제 외부 발송 활성화에 필요한 설정과 검증 절차는 인계하라.


A8. 수질 신뢰도 교차검증

공식 수질자료와 사용자 리뷰·현장 관찰의 일치 또는 괴리를 설명하는 백엔드를 구현하라.

- 공식 검사자료와 리뷰·현장 관찰을 별도 근거로 보존한다.
- 실제 리뷰 데이터의 입력 계약, 필요한 저장 구조, 분석·비교 로직과 조회 API를 구현한다.
- 같은 장소·비교 가능한 기간·대표 범위인지 확인한다.
- 수질 측정값끼리 비교할 때는 항목·단위·채수 시각·측정 방법의 비교 가능성을 확인한다.
- “탁했다”, “냄새났다” 같은 관찰 신호의 추출 근거와 분석 버전을 보존한다.
- 부정 표현, 시간 차이, 중복 리뷰, 표본 부족, 상충하는 관찰을 처리한다.
- 표본 수, 신선도, 불일치 이유, 비교 불가 사유와 원자료 출처를 반환한다.
- 리뷰를 공인 수질검사와 동등한 측정값으로 취급하거나 공식 수질등급을 덮어쓰지 않는다.
- 근거 없는 신뢰도 백분율이나 수영 안전 판정을 만들지 않는다.

실제 리뷰가 없더라도 입력·저장·분석·비교·API·테스트를 구현하라.
운영 결과는 no_review_data 등 명시적인 비교 불가 상태로 남기고, 가짜 리뷰로 채우지 말라.


B. AI 구축 선행

이번 Goal에서는 A1~A8과 이후 AI 추천·컨시어지가 공유할 백엔드 기반을 준비하라.

- 공통 장소 식별자, 활동·시간 조건, 근거가 있는 상태 스냅샷과 reason code를 제공한다.
- A 기능들을 AI가 사용할 수 있는 제한된 서비스 인터페이스로 제공한다.
- 이미 확보된 구조화 결과를 설명하는 기능이 필요하면 근거 기반 설명 계층을 구현한다.
- LLM이 관측값, 점수, 안전 판정, 수질등급, 존재하지 않는 장소나 근거를 만들어내지 못하도록 한다.
- 모델 출력은 검증하고, 실패 시 확인된 근거를 이용한 결정적 설명 또는 설명 불가 상태를 반환한다.
- provider·model 설정, timeout, 비용·호출 상한, 오류 처리를 분리한다.
- API 키는 서버에서만 사용하고 AI 입력에 인증정보와 불필요한 개인정보를 넣지 않는다.
- 앱에서 사용할 모델은 기존 설정과 서비스 요구에 맞게 선택 가능하도록 한다.

B1~B5 전체 제품 기능으로 범위를 임의 확대하지 말라.
이번 범위는 A 기능을 완성하는 데 필요한 AI 기능과 향후 확장을 위한 실행 가능한 공통 기반이다.


5. 데이터와 시스템의 필수 원칙

Pongdang은 독립 프로젝트다.
Multtara의 모듈을 import하거나 실행하고, DB·Docker network·계정·credentials에 의존하지 말라.
레거시 코드를 통째로 복사하여 독립 구현을 대신하지 말라.

현재 기술 스택을 유지하라.
- Frontend: React + Vite + TypeScript, Node.js 24
- Backend: Python 3.14 + FastAPI
- Database: PostgreSQL 18

기존 ingestion의 SourceBatch 계약, 정규화와 원자적·멱등 저장을 유지하라.
수집은 FastAPI와 분리된 worker에서 수행하고, 기존 job별 DB lock·due time·backoff·heartbeat 구조를 활용하라.
평가·알림 등 새 작업도 재시작과 중복 실행을 고려하라.

실제 데이터는 pongdang_data에 보존하고 migration은 app.schema를 통한 명시적·추가적 변경으로 구현하라.
앱 시작이나 HTTP 조회 요청에서 migration, seed, 수집, 평가 저장을 실행하지 말라.
별도 변경 기능이 필요하면 인증·권한·입력 검증을 갖춘 명시적인 경로로 구현하라.

제공기관 ID, 시간대, 발표·관측·대상·수집·만료 시각, 단위, 결측값과 revision을 보존하라.
원본 정정은 이전 근거를 superseded로 남긴다.
실패한 수집이 성공 기록을 만들거나 기존 자료의 유효기간을 연장하지 않도록 한다.
미확인 발표 시각과 값은 임의로 채우지 말라.

실제 자료가 없는 경우 더미·샘플·랜덤·과거 성공값으로 대체하지 말라.
운영 합성 데이터 생성기는 부활시키지 말라.
테스트 fixture는 격리된 테스트에서만 사용하고 운영 데이터와 명확히 구분하라.

기존 /api/data 조회 계약, allowlist, 읽기 전용 트랜잭션과 최대 100행 페이지를 유지하라.
새 기능의 읽기 API도 기존 /api/data 체계에 일관되게 추가하라.
은퇴한 /api/demo 및 /api/collector는 계속 404여야 한다.
원본 응답 전체, arbitrary SQL, import endpoint, credentials, 사용자·세션 테이블을 공개하지 말라.

기존 Compose 서비스 DNS, postgres_data volume, COMPOSE_PROJECT_NAME을 이용한 명시적 컨테이너 이름 규칙을 유지하라.
운영 DB/API 포트의 비공개 상태와 Bonifacio SSO의 access-pongdang 게이트를 보존하라.


6. 진행 방식

먼저 기능별 추적표를 만들고 작업 중 갱신하라.

각 항목에는 다음을 포함하라.
- 기능 ID와 요구사항
- 참고 근거
- 현재 구현 상태
- 필요한 데이터와 외부 의존성
- 구현할 모듈·DB·job·API
- 테스트와 검증 근거
- 프론트 연결 위치 또는 인계 항목
- 남은 제한 사항

공통 데이터 계약과 의존성을 정리한 뒤 실제 구현으로 진행하라.
독립적으로 진행 가능한 문서 분석, 모듈 구현, 테스트·검토는 서브에이전트에 나누어 병렬화하라.
공유 파일의 동시 수정을 조정하고 최종 통합과 검증은 책임지고 수행하라.

일반적인 구현 선택은 기존 코드와 요구사항을 바탕으로 판단하고 근거를 기록하라.
단계마다 진행 허가를 다시 묻지 말라.
필수 외부 정보가 없으면 관련 부분을 명확히 기록하고 독립적으로 가능한 작업을 계속하라.

장기 작업 중에도 목표·완료 항목·미완료 항목·현재 장애물·다음 검증을 짧은 진행 문서에 남겨라.
컨텍스트가 바뀌어도 기존 작업을 다시 시작하거나 빠뜨리지 말라.

범위는 위 기능의 구현·로컬 및 격리 환경 검증·연결·인계다.
운영 배포, main 병합·푸시, 운영 DB 변경, host SSH gate 설치는 별도 요청 없이 수행하지 말라.
기존 CI와 배포 규칙을 우회하지 말라.


7. 검증 기준

저장소에 정의된 명령과 실제 실행 환경을 확인하여 다음 검사를 수행하라.
- Frontend lint
- Frontend tests
- Frontend build
- Backend Ruff check
- Backend Ruff format check
- Backend tests
- 필요한 DB migration·worker·API 통합 검증

DB 테스트는 폐기 가능한 pongdang_test와 테스트 전용 접속 설정만 사용하라.
실제 운영 DB나 수집 중인 실제 DB에서 테스트와 fixture 삽입을 수행하지 말라.

기능의 실제 동작을 입증하는 테스트를 작성하라.
최소한 다음 위험과 경계를 관련 기능에서 검증하라.
- 입력부터 정규화·저장·처리·HTTP 응답까지의 연결
- 결측, 만료, 범위 밖, 외부 장애
- 중복 실행, 제공처 정정, 충돌 및 재시도
- 시간대, 날짜·연도 경계, 예보 발표 시각과 미래 정보 누출
- 장소·활동·기간·단위의 부적절한 연결
- 페이지·시간·지리 범위 상한
- GET의 쓰기 부작용 부재
- 알림 구독 권한과 중복 발송 방지
- AI의 근거 없는 출력과 실패 처리
- 프론트에 오래된 응답이나 잘못된 null 변환이 표시되지 않음

외부 API를 직접 검증할 때는 허용된 공식 endpoint와 소량의 호출을 사용하고,
실제 자료 수신 확인과 테스트 대역 통과를 구분하라.
기존 보고서의 성공 기록을 이번 작업의 실행 결과로 재사용하지 말라.

실행할 수 없는 검사는 실행하지 못한 이유와 재실행 방법을 남겨라.
테스트를 약화하거나 생략하여 완료 상태를 만들지 말라.


8. 완료 기준과 최종 인계

각 기능에서 DTO나 endpoint만 만들고 완료라고 하지 말라.
pass, TODO, 항상 빈 배열을 반환하는 임시 구현, 호출되지 않는 scaffold,
문서만 존재하는 상태는 기능 구현 완료가 아니다.

이 Goal의 완료 기준은 다음과 같다.
- A1~A8과 B 선행 기반의 필요한 백엔드 코드와 실행 경로가 구현되어 있다.
- DB, 필요한 job, 도메인 로직과 API가 실제로 연결되어 있다.
- 기존 정상 동작과 데이터 계약을 보존한다.
- 필요한 자동 테스트와 실행 가능한 통합 검증을 통과한다.
- 현재 프론트에 연결 가능한 부분은 화면 구조를 유지하며 연결되어 있다.
- 프론트가 없는 부분도 API와 검증, 인계 문서가 준비되어 있다.
- 외부 데이터·승인·자격증명·모델 검증에 남은 의존성이 명확하게 기록되어 있다.

“소프트웨어 구현 완료”, “실제 데이터 연결 확인”, “프론트 연결 완료”,
“모델 검증 완료”, “운영 활성화 완료”를 서로 구분하라.
필수 외부 의존성이 남아 실제 사용할 수 없는 기능을 실서비스 완료로 보고하지 말라.
unknown/null 처리만으로 핵심 계산이나 비교 로직의 미구현을 감추지 말라.

외부 의존성 때문에 막힌 부분은 가능한 코드·실패 처리·테스트·설정 경로를 먼저 완성하고,
무엇을 제공하거나 승인해야 어떤 검증을 재실행할 수 있는지 구체적으로 적어라.
작업량이나 컨텍스트 부족을 이유로 완료 기준을 임의로 축소하지 말라.

최종 결과는 한국어로 다음 내용을 제공하라.
- A1~A8 및 B 선행 기반의 기능별 상태표
- 실제 구현한 모듈·DB 변경·job·API
- 프론트에 연결한 부분과 수정 이유
- 화면이 없어 인계한 기능과 연결 방법
- 실행한 검사 및 결과
- 실제 데이터로 확인한 범위와 확인하지 못한 범위
- 추가로 필요한 설정·외부 승인·검증 자료
- 남은 미완료 항목과 정확한 이유

문서는 기존 문서 구조를 따라 남기고,
프론트 담당자가 요청·응답 계약, null/unknown 의미, 오류 상태와 호출 방법을 이해할 수 있게 작성하라.

이제 현재 코드와 문서를 확인하고, 추적표를 만든 뒤 실제 구현을 시작하라.
