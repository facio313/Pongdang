# 명소 상세정보 저장 · 2026-09-21

## 동작

- TourAPI의 `detailCommon2`, `detailIntro2`, `detailInfo2`를 별도 collection worker에서 수집한다. 운영시간·휴무·이용 시기·개장일·주차·시설·문의·홈페이지·소개 및 유형별 추가 항목을 정규화해 저장한다. 제공되지 않은 값은 NULL로 유지한다. 개장일을 매년의 해수욕장 개장 기간으로 해석하지 않는다.
- 기존 `collection_place` 중 상세 수집 기록이 없는 행도 대상이다. 한국어 해변·계곡을 먼저 채우며, 이후 신규 행 또는 목록의 원본 수정일/콘텐츠 유형이 바뀐 행만 조회한다. 정상 응답의 자료 없음도 저장하므로 일정 시간이 지났다는 이유만으로 다시 요청하지 않는다.
- 한국어 및 기존 외국어 TourAPI 공급자별 ID를 사용한다. 다른 공급자의 물놀이 명소는 DB 안의 한국어 TourAPI 명소와 정규화한 이름이 같고 500m 이내이며 후보가 유일할 때만 연결한다. 애매한 장소는 연결하지 않는다.
- 상세정보는 `SourceBatch`의 검증과 하나의 DB 트랜잭션을 거친다. 수정된 내용은 이전 근거를 `superseded`로 보존한다. 실패는 기존 상세정보나 수집 시각을 덮어쓰지 않으며, 15분부터 최대 24시간까지 재시도 간격을 늘린다.
- `GET /api/data/place-details?spot_ids=...`는 최대 100개 명소를 DB에서만 읽는다. 명소 목록, 모바일/데스크톱 상세, 여행 장소 조회가 저장된 정보를 사용한다. 데이터 화면에는 `place-details`, `place-detail-collection` 목록을 추가했다.
- 거리에는 고정 상세정보를 저장하지 않는다. 저장된 명소 좌표와 선택한 출발점 또는 사용자가 요청한 현재 위치로 직선거리를 계산한다. 실제 도로 이동거리·소요시간은 기존 경로 API의 별도 자료다.

## 함께 줄인 반복 호출

- 사진의 일률적인 7일 재조회를 제거했다. 저장된 TourAPI 상세의 대표 이미지/이용조건을 재사용하고, 대표 이미지가 없을 때만 `detailImage2`를 보완 조회한다. 사진 있음·없음·이용 제한을 기록해 다음 worker 실행에서도 재사용한다. 동일 원본의 동일 파일은 파일 크기/해시가 맞으면 다시 내려받지 않는다.
- 좌표→행정구역의 정상적인 결과 없음도 좌표와 함께 기록한다. 같은 좌표의 실패 없는 빈 응답은 다시 호출하지 않고, 좌표가 바뀌면 다시 확인한다. 통신 실패를 결과 없음으로 저장하지 않는다.
- 주소·좌표·명소 검색은 이미 DB 조회였다. 기상·관측·교통 등 시각에 따라 변하는 자료는 영구 상세 캐시로 바꾸지 않는다. 동시 진행 중인 livecam/점수 갱신 작업의 변경은 이 작업의 성과로 포함하지 않는다.

## 초기화와 수집

기존 독립 Pongdang 배포의 명시적 초기화 과정인 `python -m app.schema`가 추가형 v11 상세/사진/행정구역 마이그레이션을 포함한다. 전체 스키마 버전은 동시 작업의 후속 마이그레이션 때문에 더 높을 수 있다. HTTP 시작이나 조회 요청에서 스키마 생성·외부 수집을 실행하지 않는다.

Collector 설정:

| 설정 | 기본값 | 의미 |
| --- | --- | --- |
| `PLACE_DETAIL_COLLECTION_ENABLED` | `true` | 상세 보강 job 활성화 |
| `PLACE_DETAIL_BATCH_SIZE` | `50` | 한 차례에 처리할 최대 원본 명소 수. 60초가 지나면 진행 중인 한 장소를 마친 뒤 다음 차례로 넘김 |
| `PLACE_DETAIL_DAILY_BUDGET` | `500` | TourAPI 서비스별 한국 시각 하루의 상세 요청 한도 |

요청 횟수는 DB에 영속 기록한다. 일반적으로 명소당 3회가 필요하고 반복정보가 여러 페이지이면 그만큼 추가 차감한다. 한도가 부족하면 다음 날짜까지 대상이 남는다. 이 한도는 Pongdang 상세 수집의 자체 상한이며 제공처 전체 계정의 남은 할당량을 뜻하지 않는다. 키가 없거나 설정이 꺼져 있으면 job은 비활성화된다.

Worker의 정상 일정으로 기존 목록을 점진적으로 보강한다. 운영자가 명시적으로 한 묶음을 처리할 때는 같은 서버 설정으로 `python -m app.place_details`를 실행할 수 있다. `python -m app.place_details --refresh-spot <ID>`는 연결된 원본 상세와 사진을 재확인 대상으로 등록하고 한 묶음을 실행한다. 일반 대기열 우선순위와 일일 한도를 지키므로 해당 ID가 그 묶음에서 즉시 완료된다는 뜻은 아니다.
