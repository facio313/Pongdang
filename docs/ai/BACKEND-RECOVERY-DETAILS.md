# 상세 수집 복구

- 목표: 프론트 변경 없이 실제 명소 상세 초기 채움을 정상 진행하고, 일일 호출 예산과 원자료 보존을 유지한다.
- 작업: `fix/backend-operational-recovery`, 상세 collector/config/관련 테스트 담당. 운영 DB 쓰기, 수집 실행, 재시작, 커밋·푸시하지 않았다.
- 확인된 장애: 2026-09-21 14:47 KST에 상세 연결 6,604개 중 저장된 상세는 10개였다. 수집 작업은 10개 배치 후 전체 미수집 대상이 남아도 성공으로 보고했다.
- 변경: 기본 배치를 50개로 조정하고 설정 예제를 일치시켰다. 60초 이후에는 진행 중인 한 장소의 제한된 요청을 마친 뒤 다음 차례로 넘긴다. 실제 분류된 대표 해변·계곡과 연결된 상세를 먼저 처리한다.
- 제약: 서비스별 하루 500호출과 외부 수집 최소 10분 간격은 유지한다. 설정된 작은 배치는 그대로 존중한다. 이미 수집한 동일 원본은 다시 호출하지 않으며 원본 수정과 실패 재시도 규칙도 유지한다.
- 상태: 남은 즉시 처리 대상은 `partial / DETAIL_BACKFILL_PENDING`. 예산 소진은 장소별 실패 이력으로 저장하지 않고 `partial / DETAIL_DAILY_BUDGET_EXHAUSTED`로 보고하며 다음 한국 날짜로 재개를 예약한다. 다른 언어 서비스의 남은 예산은 독립적이다.
- 검증: 전용 disposable `pongdang_test`(localhost:32771), 실제 제공처 대신 테스트 응답 사용. 상세 수집/저장/provider 27개 중 26개 통과, 새 quota 날짜 테스트 1개는 미래 fetch 시각을 사용한 테스트 오류였다. 과거 KST 자정 경계로 수정한 후 해당 검증 재실행 1개 통과(5.30초); 전체 27개 검증 완료. Ruff lint/format도 통과. 기존 FastAPI/httpx 폐기 예정 경고 2개가 있다.
- 남은 일: root의 통합 검증/배포 절차. 운영 환경의 명시적 `PLACE_DETAIL_BATCH_SIZE=10` override는 별도로 확인해야 한다.
