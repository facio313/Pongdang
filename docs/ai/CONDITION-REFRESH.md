# 조건 결과 백그라운드 갱신 · 2026-09-23

## 목표와 제약

- 고정 활동점수와 표시 지표는 백그라운드에서 계산해 `condition_result`에 저장하고, 프론트의 일반 조건 GET은 완료 결과를 읽는다. 수집/계산/저장 중 또는 공급자 실패 시 기존 결과를 제공하며, 독립 지표 누락으로 정상 지표 갱신을 막지 않는다.
- 프론트 코드 변경 없음. 기존 WIP 보존. 사용자 후속 요청 “맞으면 로컬에서 다 하고 되는 거 확인하자”로 실제 로컬 `127.0.0.1:5432/pongdang` 적용·수집기 설치·서버 실행·검증까지 승인됨. 운영 변경, 커밋, 푸시 없음. `fix/finale` 미커밋 상태.

## 구현

- 스키마 v20: `condition_result`에 목록용 점수/수온/만료 칼럼과 상세 JSON을 구분하고, 완료 세대 `result_published` 표시와 원자적 게시를 사용한다. 현재/미래에서 내용이 같은 결과는 재사용하고, 지난 결과는 KST D-7까지 보관한다. 미래는 D+7까지, D-8 이전은 매 자정 정리한다.
- 완료 결과 GET은 `ready`, `refresh_after=null`로 기존 프론트 30분 재조회를 유지한다. 보존 여부는 저장값을 사용한다. 일반 GET에서 공급자 요청/점수 재계산/DB 쓰기 없음. 사용자 기준을 받는 custom POST 계산은 별도 기존 계약이다.
- 미래 예보 11개 작업은 정상 완료 후 1800초, 더 빠른 관측 주기는 유지한다. 실패 backoff도 유지하며 정확한 :00/:30 cron은 아니다. 동적 수집→조건 게시→기타/정적 작업 순서다.
- 독립 항목만 기존 component/근거/표시값으로 보완하고 정상 항목과 함께 worker에서 총점을 저장한다. 고정 독립 모델 v1에만 적용한다. 원래 관측·취득·유효 시각을 바꾸지 않으며 raw는 stale, 표시는 provisional/text로 표시한다. 값/근거가 같고 게시 시각만 달라진 부분 결과도 재사용한다.
- 명소 상세/사진은 완료 후 시간 경과만으로 재요청하지 않는다. 신규·미수집·공급자 수정·실패 재시도 대상만 처리한다. 일일 카탈로그 조회는 신규/수정 발견용이며 동일 provider ID는 기존 행에 반영한다. 실제 로컬에서 변경 없는 상세1984건/사진159건이 제외되고 다음 대상은 각각0건임을 확인했다.

## 실제 규모에서 발견해 수정한 문제

1. v19의 hard invalidation 경계 `-infinity`를 psycopg가 datetime으로 읽으면 DataError. SQL로만 재사용하는 경계를 `invalidated_at::text`로 읽어 의미를 보존했다.
2. 최초 실제 migration의 wide result/stage 반복 비교가120초 SQL timeout으로 실패했다. 전체 rollback으로 v19/legacy258770행/세대329 보존을 확인했다. 비교용 key·시간 구간·digest만 임시 테이블로 모으고 복합 인덱스를 사용한 뒤 전체 migration은151.33초에 완료됐다.
3. 브라우저에서 오늘 지난09/12/15/18시 예보 누락 발견. live merge의 과거 stage 제거가 legacy backfill에도 적용되던 문제였다. 최신 legacy를 우선 반영하고, 기존 경계로 나눈 뒤 D-7 내 누락 과거만 채우도록 수정했다. 무효화 경계 이전만 허용한다. 이미 저장된 과거 및 현재/미래는 바꾸지 않는다. 명시적 `repair_condition_result_history`로 로컬 누락23790행을32.79초에 복원했다.
