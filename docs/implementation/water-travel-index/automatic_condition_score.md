# 자동 활동 조건 참고 점수

구현일: 2026-09-16 KST · 모델 `pongdang-activity-conditions` / `1.0.0`

## 이번 연결에서 점수가 없었던 이유

`water_index/registry.py`의 과학적 평가 모델은 `unimplemented`이며 기존 연구·설계 단계에서 수치 함수를 활성화하지 않았다. `ConditionsEnvelope.environment_score`도 항상 `null`이었다. 별도로 구현된 `POST /api/data/water-index/condition-score`는 사용자가 범위·중요도를 직접 입력하는 조건 일치 계산이다. 제품 화면은 자동 점수를 기대하면서 항상 비어 있는 `environment_score`를 읽고 있었다.

이번 구현은 `GET /api/data/water-index/conditions`에 자동 계산 결과 `condition_score`를 추가한다. 기존 과학적 평가의 상태·점수와 사용자 지정 계산의 수식은 유지한다. 새 모델은 **실제 수집 자료를 공개된 참고 기준에 대입하는 미보정 정보 지수**다. 안전 확인, 운영 허가, 검증된 개인 적합도 또는 여섯 활동 사이의 동일한 효용 척도가 아니다.

## 계산 기준과 총점

활동별 항목은 기존 데이터 계약의 단위와 목록을 따른다.

| 활동 | 총점 구성 항목 |
|---|---|
| 수영 | 수온, 방문 기온, 풍속, 파고 |
| 서핑 | 수온, 방문 기온, 풍속, 파고, 파주기 |
| 휴식 | 방문 기온, 상대습도, 풍속, 1시간 강수량 |
| 갯벌 | 야외 기온, 풍속, 1시간 강수량; 운영창·조석·귀환 조건은 별도 |
| 온천 | 시설 실측 욕조 수온, 야외 방문 기온; 실내 온도·시설 운영은 별도 |
| 래프팅 | 하천 수온, 야외 기온, 풍속 및 수위·유량 항목. 수위·유량은 지역 운영 기준 미설정으로 점수화하지 않음 |

**풍속**은 원문 Table 6을 다음처럼 구간 적용한다. 변환한 km/h를 소수 첫째 자리에서 처리한다. `0–0.5→80`, `0.6–9.9→100`, `10–19.9→90`, `20–29.9→80`, `30–39.9→60`, `40–49.9→30`, `50 이상→0`. 음수를 0으로 제한한 것과 일별 모델의 시간별 전이는 제품 변형이다.

그 외 항목은 아래 `(자료값 → 참고점수)` 절점 사이를 선형 보간하고, 바깥에서는 끝점 점수를 사용한다. **방문 기온의 범위 이외 절점은 문헌에서 추정한 계수가 아니라 명시적인 제품 기본값**이다.

| 항목 | 절점 |
|---|---|
| 해변 방문 기온 °C | `21→0, 25→100, 30→100, 33→0` |
| 갯벌·온천·래프팅 야외 방문 기온 °C | `5→0, 15→60, 20→100, 27→100, 32→50, 38→0` |
| 수온 °C | `10→0, 18→40, 24→85, 27→100, 30→80, 35→0` |
| 상대습도 % | `0→40, 30→85, 40→100, 65→100, 85→50, 100→20` |
| 1시간 강수량 mm/1h | `0→100, 0.5→90, 2→60, 5→20, 10→0` |
| 수영 파고 m | `0→100, 0.3→100, 0.8→70, 1.5→20, 2→0` |
| 서핑 파고 m | `0→0, 0.3→30, 0.6→80, 1→100, 1.5→80, 2→40, 3→0` |
| 서핑 파주기 s | `3→0, 5→30, 8→80, 10→100, 15→100, 20→70` |
| 시설 욕조 수온 °C | `30→0, 36→70, 38→100, 40→50, 42→0` |

총점은 **확보한 항목 점수의 동일 가중 산술평균**이며 소수 첫째 자리 반올림한다. 중요도 추정 자료를 확보하지 않았으므로 임의의 차등 가중치를 논문 계수처럼 제시하지 않는다. 각 항목과 총점에서 반올림한다.

- 전 항목 계산 가능: `evaluated`.
- 일부 항목만 계산 가능: `partial`, `coverage=계산한 항목 수/예정 항목 수`. 누락 항목에 임의 점수나 0을 넣지 않는다. 같은 확보 항목끼리 비교해야 한다.
- 계산할 항목 없음: `unavailable`, 총점 `null`.
- 공식 제한 또는 활동 미지원 확인: `blocked`, 총점 `null`.
- 모델 검증 상태는 계속 `not_evaluated`다. 소프트웨어 테스트의 통과가 실제 만족·사고 예측의 검증을 뜻하지 않는다.

정확한 실행 기준은 [`activity_score.py`](../../../backend/app/water_index/activity_score.py)에 버전과 함께 묶여 있으며, 각 API component의 `criterion`, `source_ids`, 최상위 `sources`, `methodology`로 그대로 설명한다.

## 실제 자료를 연결하는 규칙

1. 기존 지점에 직접 연결된 관측소 또는 승인된 대표 관측소가 있으면 그 연결을 사용한다. 기존 scientific assessment 및 매핑 테이블을 수정하지 않는다.
2. 연결이 없는 실제 장소는 **별도 `context_metrics`**를 읽는다. 장소 좌표로 확인되는 기상청 동일 5km 격자의 provider ID 또는 **10km 이내 실제 좌표가 있는 관측소**를 최대 6개 조회한다. 활동별 provider와 요청 관측/예보 모드·항목을 제한한 뒤 페이지 상한을 적용한다. 좌표가 없으면 근접으로 취급하지 않는다.
3. `context_metrics`는 `nearby_station_context` 또는 `containing_forecast_grid`이며, 장소 실측·대표성을 확인한 자료가 아니다. `condition_score`에는 관측소 이름·관계·거리를 보존한다. 기존 `metrics` 및 사용자 지정 범위 계산에 주변 자료를 몰래 넣지 않는다.
4. 원래 대상 시각/기간이 현재 요청을 포함하고, 수집/알려진 발표 시각이 조회 기준보다 늦지 않으며, 정상 숫자·단위·공간 설명이 있는 자료만 계산한다. 결측·만료·서로 다른 값의 충돌은 계속 제외한다.
5. KHOA 활동예보는 발표 시각을 제공하지 않는다. strict metric의 `unknown/provider_issue_time_unknown`과 원 `issued_at:null`을 유지하면서 **이 참고 모델에서만** 다른 계약을 모두 만족한 대상 예보를 사용하고 경고를 보존한다. `fetched_at`을 발표 시각으로 대체하지 않는다.
6. KHOA 서핑의 숙련별 행이 같은 장소·대상 기간에서 동일 기상값을 반복하면 그 값을 한 번 점수화한다. 모든 원 evidence는 유지하고 `identical_provider_variants`를 표시한다. 다른 값·단위·기간, 미지원 활동, 해수의 하천/욕조 전용은 허용하지 않는다.
7. GET에서는 자료 수집·외부 호출·스키마 변경·매핑/점수 저장을 수행하지 않는다. API 응답은 `no-store`이며 조회마다 실제 자료의 유효성을 확인한다.

## 검증

새 단위 테스트는 논문 수치 적용, 총점·부분 확보율, 여섯 활동, 소스 재검증, 알려지지 않은 발표 시각, 동일/충돌 변형, 공식 제한, 수역/시설 범위, 결측 처리를 확인한다. 새 `pongdang_test` DB 통합 테스트는 실제 저장 계약을 통해 HTTP GET을 호출하여 지점/관측소 분리, 주변 자료의 별도 표시, 동일 기상청 격자, 좌표 없는 관측소 제외, 반경과 활동/모드 조회 상한, 읽기 중 DB 쓰기 없음을 검증한다.

운영 자료가 전국 모든 장소에서 이미 확보되었다거나, 모든 날짜에 예보가 있다는 보장은 아니다. 기존 수집 지역·기관 승인·유효기간 밖에서는 숫자 대신 누락 사유를 계속 표시한다. 특히 래프팅 수위/유량 운영 범위와 온천 시설 욕조 실측은 별도 수집·현장 기준이 필요하다.
