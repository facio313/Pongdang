# A1 전체 활동 선택·종합 조건 점수 구현 및 검증

2026-09-14 KST. 사용자 결정: 수영·서핑·휴식·갯벌·온천·래프팅 전체를 대상으로 하고, 종합은 **선택한 활동 안의 여러 조건 합산**으로 제공한다. 이 문서는 이전 A1의 첫 지점·수영 고정 요약보다 뒤의 구현 상태를 기록한다.

## 구현한 결과와 남은 경계

Water Index 허브에서 장소, 여섯 활동, 관측/공식 예보, 대상시각(KST)을 선택하고 실제 자료·지원/제한 상태·결측/만료 사유를 볼 수 있다. 사용자가 선택한 조건의 관측소·목표 범위·중요도를 입력하면 서버가 실제 collection 자료를 읽어 **종합 조건 일치 점수**를 계산한다. 조건별 값·범위 충족 여부·가중 기여와 원자료 revision·시간·단위·공간 근거를 함께 반환한다.

이 기능은 입력한 조건의 산술 일치율이다. 여섯 활동의 과학적 환경 적합도 모델, 실제 만족/안전 예측을 완성한 것은 아니다. 기존 레지스트리는 여전히 `unimplemented/not_evaluated`이고 `environment.score`는 null이다. 사용자 요청을 임의의 과학적 가중치·이상 수온을 만들 근거로 사용하지 않았다. [활동별 1차 근거 검토](activity_model_evidence.md)와 [자료 계약·실증 검증에 필요한 입력](activity_data_validation.md)에 남은 근거를 기록했다.

| 활동 | 선택 가능한 명시 조건 | 추가로 필요한 현장 근거 |
|---|---|---|
| 수영 | 수온·외부 기온·풍속·파고 | 실제 수영 구역·운영/입수/수질·이안류 제한, 노출·장비·대상자별 검증 |
| 서핑 | 수온·외부 기온·풍속·파고·파주기 | 브레이크 대표성·파향/풍향·숙련/장비·실제 세션 결과 |
| 휴식 | 외부 기온·상대습도·풍속·1시간 강수량 | 휴식 구역·접근 통제, 활동/노출별 쾌적성·만족 표본 |
| 갯벌 | 외부 기온·풍속·1시간 강수량 | 실제 경로·공식 운영창·조석/침수/안개 통제, 활동 결과 표본 |
| 온천 | 시설 욕조 수온·외부 기온 | 시설 유형·실제 욕조 측정·위생/이용 제한·체류/대상별 결과 |
| 래프팅 | 하천 수위·하천 유량·하천 수온·외부 기온·풍속 | 승인 운항 구간·수리 관계·상류/방류/구간 통제·장비/숙련별 검증 |

표에 조건이 등록된 것과 해당 장소에서 실제 자료를 확보한 것은 다르다. 없는 자료는 목록에서 미확보로 표시한다. 온천 욕조 수온을 해수로 대체하지 않으며, 래프팅의 수온·수위·유량은 확인된 하천 관측소 종류에 한정한다. 파고의 제공기관별 의미와 원공간 범위는 출처와 함께 해석해야 한다. 현재 수집 경로에서 시설 욕조 수온은 확보되지 않았다.

## 계산 계약

`explicit-range-match@1.0.0`, `water-conditions.v1`.

- 사용자가 조건별 최소/최대 중 하나 이상과 유한한 양의 중요도를 명시한다. 범위와 중요도에 자동 기본값은 없다.
- 경계를 포함해 실제 수치가 범위 안이면 1, 밖이면 0이다. 종합은 `100 × Σ(중요도 × 충족 여부) / Σ중요도`이며 Decimal을 사용해 소수 첫째 자리에서 half-up 반올림한다.
- 선택한 조건 하나라도 결측·만료·미확인 단위/공간·충돌이면 `incomplete / score=null`이다. 유효한 나머지 조건만으로 분모를 줄이지 않는다.
- 공식 제한 또는 활동 미지원 근거가 있으면 `blocked / score=null`이다. 활동 지원·안전이 unknown인 경우 상태와 필요한 근거를 그대로 표시하고, 숫자는 선언 조건 비교로만 해석한다.
- 환경 적합도·안전 점수·활동 간 순위와 필드를 공유하지 않는다. 모든 기준을 충족한 100점도 활동 가능 또는 안전을 뜻하지 않는다.
- 조건은 1~8개, 중복 지표는 금지, 중요도는 0 초과 1000 이하다. 결과와 입력·모델을 담은 계산 해시를 반환한다.
- 사용자 기준은 요청에 포함되고 계산 결과에도 그대로 반영된다. 서버 사용자 설정 저장이나 기존 환경 평가 테이블의 수치 공개는 추가하지 않았다. 화면 재진입/활동 변경 시 조건을 다시 설정한다.

## API와 데이터 흐름

모든 경로는 외부 운영에서 `/pongdang` 아래에 위치한다. [현재 OpenAPI](openapi.json)를 갱신했다.

| API | 역할 |
|---|---|
| `GET /api/data/water-index/activities` | 여섯 활동·조건 카탈로그, 점수 의미·산식, 필요한 현장 근거 |
| `GET /api/data/water-index/conditions` | `spot_id, activity, mode, at?, as_of?`에 맞는 실제 자료와 근거/상태 |
| `POST /api/data/water-index/condition-score` | 동일 조회 조건과 `criteria[{metric,station_id,minimum,maximum,weight}]`의 조건 일치 점수 계산 |

POST는 저장·수집을 수행하지 않는 계산 요청이다. 본문으로 관측값·점수·모델 활성화 값·임의 SQL을 받을 수 없다. 본문은 JSON 16KiB 이하, 중복 키·추가 필드·비유한 수치는 거절한다. 조회는 기존 DataReader의 repeatable-read/read-only 트랜잭션과 SQL timeout을 사용한다. 지점 1개, 관측소/지표/근거 각 최대100개, 대상시간과 지식 cutoff 차이는 최대31일이다. observation의 미래 대상과 미래 as_of는 거절한다.

정정본을 먼저 선택한 뒤 값의 결측·만료를 검사한다. 최신 정정에서 지표가 완전히 제거된 경우에도 이전 다른 관측값으로 돌아가지 않는다. 같은 관측소/지표/대상시각의 여러 독립 기록은 충돌로 보류한다. 발표시각 미상의 예보를 임의 시각으로 보완하지 않는다. 활동 전용 제공자료를 다른 활동으로 전용하지 않는다.

기존 수집기의 A→B→A 복귀는 원 A의 fetched_at을 보존하고 현재 상태만 복원하므로 복귀시각 이력이 없다. 최신 생성본과 현재 활성본이 불일치하면 새 API는 `revision_reactivation_history_unavailable`로 보류한다. 현재/과거 어느 시점에 A가 다시 활성화됐는지 추측하지 않는다. 이 한계의 해소에는 별도의 명시적 수집 이력 확장이 필요하다.

추가 DB migration, 생산 자료 쓰기, 새 worker/job은 없다. 실제 원자료 저장·정정과 기존 authority/mapping 계약을 재사용하고, 사용자별 임시 기준의 계산을 기존 과학 평가 결과로 저장하지 않는다.

## 프론트 연결

[ActivityAssessmentPanel.tsx](../../../frontend/src/ActivityAssessmentPanel.tsx)를 Water Index 허브에 연결했다. 기존 메뉴·라우팅·관련 원자료표를 보존하며 다른 기능 페이지는 이번 요청 범위에 따라 변경하지 않았다.

1. 장소 목록은 기존 water-twin의 최대25개 페이지로 읽고 사용자가 선택한다.
2. 활동과 관측/예보·대상시각을 선택하면 해당 조건 자료를 읽는다.
3. 필요한 조건·관측소·범위·중요도를 사용자가 선택한 뒤 종합 계산을 요청한다.
4. 점수와 조건별 근거, 지원/제한 미확인, 환경 모델 미검증을 함께 표시한다.
5. 조건·장소·활동·시각 변경 시 기존 점수를 즉시 제거하고 진행 중 요청을 취소한다. 늦은 응답을 다른 선택의 결과로 표시하지 않는다.
6. 읽기/계산은 `BASE_URL`을 사용한다. 서버 계산에는 표시된 근거의 `at/as_of`를 보내고 응답의 활동·장소·시각·조건·수치 의미를 검사한다.
7. 사유는 한국어 문장으로 표시하고 원본 코드는 접힌 상세에 보존한다. 단위·제공기관·레코드 ID·측정/발표/수집/유효시각은 근거 표에서 확인한다.

주요 파일은 [계산 모델](../../../backend/app/water_index/conditions.py), [읽기 API](../../../backend/app/water_index/condition_api.py), [프론트 계약 client](../../../frontend/src/activityAssessmentApi.ts)다.
