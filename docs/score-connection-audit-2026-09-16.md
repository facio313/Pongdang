# 점수·API 연결 수정 및 운영 확인

점검일: 2026-09-16 KST. 작업 브랜치: 기존 `feature/connect`.
기준 커밋: `28a0853a80dc313b4a4e0d05242c7121cf12f2a9`.
작업 폴더는 `Pongdang-connect`이며 다른 `Pongdang/dev` 폴더의 미커밋 작업은 보존했다.
CSS 파일 변경은 없다. 비밀 값·인증 URL·원본 제공자 응답은 이 문서에 포함하지 않는다.

## 점수가 비어 있던 이유

1. 기존 `water_index/registry.py`의 과학적 종합 모델은 `unimplemented`, 활동 프로필은 `unapproved`였다. 연구·설계·수집·상태 평가가 구현되어 있어도 실행 가능한 종합 점수 함수가 승인되어 있는 상태는 아니었다.
2. `POST water-index/condition-score`에는 사용자가 정한 범위와 중요도를 비교하는 계산기가 있었다. 제품 화면은 이 경로를 호출하지 않고, `GET water-index/conditions`의 항상 비어 있던 `environment_score`를 읽었다.
3. 여행 장소와 제공자 관측소는 별개의 ID이다. 대표 관측소 연결이 없는 여행 장소는 원자료가 DB에 있어도 `metrics=[]`로 반환됐다.
4. 해양조사원 해변·서핑 자료는 예보이다. 현재 관측만 요청하면 나오지 않는다. 제공자가 발표 시각을 주지 않는 자료는 기존 엄격한 평가 계약에서도 보류됐다.
5. 홈·오늘·추천·지도 및 저장 코스 일부 점수 칸은 서버 계산값을 읽지 않거나 `null`을 고정해 사용했다.
6. 실제 카카오 장소는 `type=beach_search_result`, 빈 `region`, 주소에만 `강릉`이 있는 경우가 있었다. 기존 홈 조회는 지역 검색과 `type=beach` 필터에서 장소를 누락해 점수 요청을 시작하지 못했다. 기존 읽기 전용 분류 장소 API로 해변·계곡을 선택하도록 연결했고, 자료 탐색의 검색 허용 컬럼에 기존 `address`도 추가했다. 주변 약국·카페를 해변으로 바꾸지 않는다.

## 수정한 계약

- `GET water-index/conditions`가 `condition_score`로 **활동 조건 참고 점수**를 반환한다. 수영·서핑·휴식·갯벌·온천·래프팅 각각 항목 점수, 총점, 계산 기준, 출처, 확보한 항목 비율, 보류 사유를 포함한다.
- 논문에서 가져온 근거와 제품에서 정한 점수화 규칙을 분리한다. 모델 버전과 각 기준은 API 및 화면의 `분야별 점수·산정 기준·출처`에서 확인할 수 있다.
- 자료가 있는 항목으로 부분 점수를 계산하면 부분 계산 사실과 자료 확보율을 표시한다. 결측·만료·충돌을 0점이나 정상 상태로 바꾸지 않는다.
- 대표성 검토가 없는 주변 자료는 별도의 `context_metrics`로 제공하며 관측소명·거리·격자 범위를 표시한다. 해당 장소의 실측이나 검토된 대표 자료로 등록하지 않는다.
- 관측 점수가 없을 때 현재 시각의 예보를 따로 조회하고 화면에 `예보`라고 표시한다. 확인된 제한이 있으면 예보로 우회하지 않는다.
- 기존 안전 판단과 `environment_score` 계약은 별도다. 이 참고 점수를 안전 확률이나 현장 검증을 마친 모델로 설명하지 않는다.

전체 절점·총점 수식·논문 적용 위치와 한계는 [자동 활동 조건 참고 점수](implementation/water-travel-index/automatic_condition_score.md)에 기록했다.

### 실제 수집 자료의 화면 확인

위 정규화 자료만 폐기 가능한 로컬 `pongdang_test`에 적재하여 실제 카탈로그 장소 ID로 API와 화면을 확인했다. 승인 관측소 매핑은 전후 0개였으며 GET은 매핑·점수·근거를 저장하지 않았다.

- 04:30 KST 홈: 실제 경포해수욕장 선택, 수영 참고 점수 **67.1**, 확보율 **100%**, `예보`와 주변 관측소·동일 격자 근거 표시.
- 04:31 KST 오늘: 수영 **67.1**, 서핑 **54.8**, 나머지 활동은 확보율과 지원 미확인 상태를 포함해 표시. 예를 들어 갯벌의 일부 기상 항목 100점은 확보율 33%이며 갯벌 체험 가능 여부가 아니다.
- 수영 상세: 수온 23.4°C→80.5점, 기온 17°C→0점, 풍속 0.9m/s→100점, 파고 0.5m→88점. 평균 `(80.5+0+100+88)/4=67.125`를 소수 첫째 자리로 반올림하여 **67.1**.
- 계산 기준, 버전, 논문 링크, 미보정 제품 기본값 설명을 브라우저에서 펼쳐 확인했다. 별도 원자료 표가 비어 있어도 주변·격자 예보 점수가 있는 경우를 구분하여 안내한다.

이는 실제 외부 자료 → 테스트 DB → 조건 API → 제품 화면의 연결 증거이며 운영 컨테이너의 화면 검증과는 구분한다.

## 웹캠과 다른 연결 오류 수정

- 명시적인 장소 주변 조회에서 2km 안의 도시·공항 카메라를 받았다는 이유로 검색을 끝내던 오류를 수정했다. 물 카메라가 없으면 다음 허용 반경을 확인한다. 최대 3개 반경·추가 페이지 없음은 유지한다. 아래 후속 요청에 따라 기본 웹캠 화면은 이 주변 조회를 사용하지 않는다.
- Windy 재시도 대기 중에도 최초 인증·권한·제공자 제한 오류가 유지되며, 서버 자체 일일 예산과 제공자 한도를 구분한다.
- 카카오 SDK가 반환하는 `키 없음`, `도메인/연결 실패`, `응답 지연` 메시지를 화면이 일반 오류로 덮어쓰지 않는다.
- 저장·추천 요청에서 SSO 로그인 HTML/리다이렉트를 API 성공으로 처리하지 않는다. SSO 서버 설정 부족, 허용 요청 출처 부족, 여행 저장소 장애를 구분해서 표시한다.
- 리다이렉트 없는 502/503/504 HTML 장애 응답은 서버 장애로 안내하며 로그인 만료로 오진하지 않는다.

## 사용자가 운영에서 확인할 사항

운영 배포 스크립트는 **`/home/cks/.config/pongdang/production.env`**를 사용한다. 이 컴퓨터의 `.env`에 키를 넣어도 운영으로 자동 복사되지 않는다. `.env`를 Git에 커밋하지 않는다.

|---|---|---|
| 웹캠 목록·타임랩스 | `WINDY_WEBCAMS_API_KEY`에 **Webcams API 전용 키**. [Windy 키 관리](https://api.windy.com/keys)에서 발급/조회. Map Forecast 키와 구분 | 로컬 저장 키 인증 성공, 운영 적용 여부 미확인 |

| 날씨·수온·파고 | collector의 `DATA_GO_KR_KEY`, `KMA_API_HUB_KEY`와 각 서비스 활용 신청 승인·관측소/수집 위치 설정 | 로컬 주요 기상·해양 API 성공. 운영 worker heartbeat와 개별 job 상태 확인 필요 |

지도 등록 절차는 [Kakao 지도 공식 가이드](https://apis.map.kakao.com/web/guide/), 웹캠 제품 구분은 [Windy 공식 문서](https://api.windy.com/webcams/docs)를 따른다.

## 운영 반영·검증 순서

1. 이 수정본의 frontend lint/tests/build 및 backend Ruff/tests, 브라우저 검사를 통과시킨다.
2. 기존 브랜치 흐름을 따라 검증한 커밋을 `main`에 반영하고 CI의 배포 작업까지 확인한다. CI를 건너뛰어 호스트에서 코드를 덮어쓰지 않는다.
3. 운영 환경 설정은 위 지정 파일에서 확인한다. 기존 host SSO snippet의 검토/설치는 앱 배포와 별도다.
4. 로그인한 화면에서 홈·오늘·추천·지도·저장 코스와 웹캠을 확인한다. 점수 응답의 `condition_score`, `coverage`, 근거 관측소, `mode`와 화면이 같은지 비교한다.
5. 값이 없으면 collector heartbeat와 해당 수집 job의 오류·마지막 성공·자료 만료를 확인한다. 오래된 heartbeat를 정상 수집으로 판정하지 않는다.
6. 결과를 공유할 때는 HTTP 상태·정제된 오류 코드·점수·확보율·설정 **존재 여부**만 전달한다. `.env`, 전체 `docker inspect`, 토큰·키 값은 출력하지 않는다.

현재 운영 접속 제한 때문에 새 코드의 운영 화면 반영까지 확인한 상태는 아니다. 로컬 회귀검사, 실제 제공자 호출, 운영 배포/화면 확인을 각각 구분해서 판단해야 한다.

| Playwright 실제 브라우저 회귀 테스트 | **18개 통과** |
| CSS | 파일 변경 없음, 빌드 산출물 `index-HbuXCFji.css` 동일 |
| 실제 제공자 자료의 API·화면 | 경포 점수와 근거·출처 표시 확인 |

브라우저 회귀에는 실제 제공자와 같은 카탈로그 유형·빈 지역/주소 검색, 제한 상태의 예보 우회 방지, 7일 날짜별 점수, 저장 코스의 실제 방문 시각, 조회 범위 밖 일정, 만료 시 이전 값 제거, 기존 추천·저장·지도·즐겨찾기·알림 흐름이 포함된다. 테스트 서버와 임시 DB는 이 작업에서 만든 로컬 인스턴스만 사용했다. 운영 DB·스키마·환경 파일은 변경하지 않았다.

초기 구현 검증은 기존 `feature/connect` 작업 디렉터리에서 완료했다. 이후 사용자가
운영 배포를 요청했으므로 기존 `dev`·`main`과 CI 배포 경로로 반영한다. 이 문서의
로컬 제공자·화면 검증 기록과 실제 운영 배포 결과는 구분하며, 배포 결과는 해당
커밋의 GitHub Actions 실행 기록으로 확인한다.

## 후속 요청: 위치와 무관한 무작위 물 풍경

사용자 요청에 따라 기본 웹캠을 위치·거리 기준에서 무작위 물 풍경 목록으로 바꿨다.
해변·해안·항구·호수·하천의 실제 제공자 분류를 사용하고, 기본 카탈로그에서는 장소 DB
조회나 근접 순위 계산을 하지 않는다. 홈에는 열 수 있는 카메라 3개를 무작위로 표시하며,
카드를 누르면 해당 카메라의 타임랩스 또는 원본 페이지로 바로 연결한다.

`다른 풍경 보기`는 순서를 다시 섞는다. 전체 목록의 분류·페이지 탐색에서는 같은 순서를
유지하고, 재섞기는 1페이지로 돌아간다. 유효한 10분 캐시 안에서는 순서 변경 때문에
Windy API를 추가 호출하지 않는다. 다섯 분류의 첫 25개 제한과 호출 예산은 유지한다.
화면 CSS는 변경하지 않았다. 상세 계약은 [웹캠 안내](webcams.md)를 따른다.

추가 브라우저 회귀 3개는 홈 3개 카드의 정확한 카메라 링크, 무작위 목록의 분류·페이지·
재섞기, 홈 조회가 진행되는 동안 전체 목록으로 이동할 때 요청이 겹치지 않는지를 검증한다.
카메라 ID와 seed가 같으면 캐시 갱신 뒤에도 상대 순서가 유지된다. 무작위 카탈로그와
페이지 이동 시험은 명시적인 오프라인 카메라 fixture를 사용하며 실제 제공자 재생 확인과
혼동하지 않는다.

## 운영 후속 수정: 기본 해수욕장 선택

`강릉` 지역 검색만으로는 지역·주소가 비어 있고 이름만 `경포`인 해양조사원 자료를
찾지 못했다. 이때 홈은 빈 목록을 로딩 상태처럼 `장소 확인 중`으로 표시했다.

`GET /api/data/water-index/default-place`는 기존 DB의 실제 해변에서 경포 후보 최대
3개와 다른 해수욕장 후보 최대 5개를 읽는다. 경포 관측·예보로 참고 점수를 계산할 수
있으면 기본으로 선택한다. 경포 자료가 없거나 만료됐다면 실제 점수를 계산할 수 있는
다른 해수욕장으로 전환한다. 다른 후보 중에서는 현재 자료와 해운대·광안리·대천·속초·
낙산·송정 이름을 우선한다. 점수 계산은 기존 결측·만료·단위·충돌 검사를 그대로 거친다.
경포의 공식 제한은 자료 없음으로 취급해 숨기지 않는다.

홈·오늘은 `강릉 경포대 해수욕장`을 기본 표시하고 선택된 실제 ID로 모든 조건을 조회한다.
대체 장소를 사용하면 표시 이름과 지역도 함께 바꾼다. 모든 자료가 없으면 실제 장소나
점수를 만들어 넣지 않고 자료 없음과 수집기 확인 안내를 표시한다. 조회 오류·시간 초과도
화면에 표시하여 무한 로딩처럼 남지 않는다. 지도 기본 선택도 같은 서버 결과를 사용한다.

이 경로는 읽기 전용이며 API 호출에 따른 수집·DB 쓰기·시딩은 없다. 기본 장소 선택에
Windy 또는 카카오 키가 필요하지 않다. 실제 자료가 하나도 없는 운영 DB까지 점수가
생긴다는 의미는 아니며, 그런 경우 수집 작업 상태를 확인해야 한다. CSS는 변경하지 않았다.
